# Hammer CLI release

The Foreman release team maintains [hammer-cli](https://github.com/theforeman/hammer-cli) and [hammer-cli-foreman](https://github.com/theforeman/hammer-cli-foreman). Foreman's generic branch, version-bump, and tag scripts do not cover them. Perform these steps separately for core and plugin, including for patch releases when needed.

## Decide and prepare

1. Compare each stable or development branch with its last published tag. Review user-facing changes, compatibility, the plugin gemspec's core dependency, release notes, and packaging needs. Decide and record the version for each gem; a new core release is not automatically required just because Foreman has a new version. Confirm that the chosen core version satisfies the plugin and stable packaging dependencies.
2. For a new series, create and verify each `<series>-stable` branch from its reviewed source. Prepare version and release-note changes on the appropriate stable branch. After branching, separately prepare next-development version bumps on master. Use the repositories' review and branch-protection process.
3. Run the repository test suites and CI matrix for the candidate commits. Test the selected core and plugin together against the target Foreman version. Exercise populated parameters in human, JSON, YAML, and CSV output: compare keys and fields, including undeclared fields such as `is_property`, and check that CSV flattening is intentional. The 5.1.0 plugin had a known regression affecting human/JSON/YAML output and omitted fields ([release notes](https://github.com/theforeman/hammer-cli-foreman/blob/5.1.0/doc/release_notes.md)). A subsequent [fix](https://github.com/theforeman/hammer-cli-foreman/pull/671) was later [reverted](https://github.com/theforeman/hammer-cli-foreman/pull/673); check the fix and its containment in the version being released. Resolve regressions or obtain an explicit release-owner exception and document its user impact and follow-up; a passing unit suite alone is insufficient.
4. Before a translation update, inspect the candidate's `gettext:find_new` implementation. The [5.1.0 implementation](https://github.com/theforeman/hammer-cli/blob/5.1.0/lib/hammer_cli/i18n/find_task.rb) can overwrite existing PO catalogs, and `tx:update` invokes it. Do not run it against valuable catalogs until a reviewed safeguard is present and tested; retain a recoverable clean checkout and review the locale diff. The [catalog safeguard](https://github.com/theforeman/hammer-cli/pull/411) is a useful reference, not proof that a particular stable branch contains it.
5. Check actual compiled MO catalogs in the candidate gem against its PO sources and intended translation update, not just their presence or file count. For example, unpack a locally built candidate with `gem unpack`, inspect the locale files, and use `msgunfmt` and `msgfmt` to compare compiled messages with the reviewed PO files. Investigate stale headers and unchanged content; the 5.1.0 gems included compiled catalogs but freshness was not established. Record any accepted translation limitation.

## Publish and verify

Publishing requires permission to push to the upstream repositories and the configured GitHub Actions `release` environment and RubyGems trusted publisher. Before any tag push, inspect the workflow **at the candidate commit**, confirm the intended tag and whether it will publish, and obtain release authorization. Check for an existing tag and gem version first; do not move or reuse a published tag.

The historical 5.1.0 core [workflow](https://github.com/theforeman/hammer-cli/blob/5.1.0/.github/workflows/release.yml) triggers on every pushed tag, builds a gem and man page, checks that the gem filename matches the tag, and publishes via trusted credentials. The [plugin workflow](https://github.com/theforeman/hammer-cli-foreman/blob/5.1.0/.github/workflows/release.yml) delegates publication to `voxpupuli/ruby-release`. Inspect the action and current workflow before releasing; do not assume their behavior is unchanged. Trusted publishing uses OIDC for authorization, not proof of gem signing. Do not run a second manual `gem push` alongside the workflow.

1. Verify the exact version in each gemspec/version file, the stable commit, release notes, and local and remote tag state. The 5.1.0 Hammer tags were lightweight and named exactly `5.1.0`, unlike the signed annotated tags created by Foreman's generic script. Confirm the current repository tag policy and workflow before creating the exact version tag; do not assume Foreman's signing policy applies to Hammer.
2. Push the approved tag and watch the corresponding upstream Actions run, including its build, release, environment approval, and propagation steps as applicable. If it fails or is ambiguous, stop and inspect Actions and RubyGems before retrying; do not push a replacement tag or gem blindly. Coordinate recovery with maintainers, since publication may already have occurred.
3. Record each repository, exact tag and commit, Actions run URL and outcome, RubyGems version URL, and SHA-256. Download the published gem and compare its SHA-256 with RubyGems metadata; where the workflow retains the built artifact, compare it too. Verify gem version, dependencies, executables, and locales. If evidence differs or the artifact has expired, investigate and record the limitation before packaging.
4. Update stable RPM and Debian packaging to the chosen published versions, including dependencies. Verify the final release builds and staging contents. Publication of a gem or a successful build does not itself prove package installability.
